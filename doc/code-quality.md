# Качество кода как часть обучения

Маша с первых занятий учится писать код, который можно понять, проверить и изменить. Эти требования входят в задание и его приёмку. Codex объясняет и проверяет; имена, файлы, компоненты и исправления Маша создаёт сама.

## Понятные имена

Имя должно отвечать, что хранится в значении, что делает функция или за что отвечает компонент. Использовать английские слова, последовательные термины предметной области и обычные соглашения языка.

| Что именуем | Соглашение проекта |
|---|---|
| Переменные, функции и методы JavaScript/Java | `camelCase`; значение — по смыслу, действие — с глаголом |
| React-компоненты и их файлы | `PascalCase`, совпадающее имя компонента и файла `.jsx` |
| Java-классы и интерфейсы | `PascalCase`; имя отражает назначение |
| Java-пакеты | Строчные имена, соответствующие структуре пакетов |
| CSS-классы | `kebab-case`, с понятной областью применения, например частью имени компонента |
| Модули JavaScript без компонента | `camelCase`, имя по назначению, расширение `.js` |

- Различать один объект и коллекцию, объект и его идентификатор, название и сами данные. Для коллекций использовать множественное число. Логические значения называть так, чтобы было понятно проверяемое условие, например с `is`, `has` или `can`.
- Имена `data2`, `temp`, `obj` и подобные требовать уточнить, если по месту использования непонятно, что они означают. Короткий локальный индекс допустим, когда его роль очевидна. Не вводить формальный запрет на любое короткое имя.
- Не оставлять случайные сокращения, транслит, опечатки и разные названия одного понятия. Если имя обещает одно, а значение или действие другое, это обязательное замечание.
- Имена импортов также отражают назначение: компонент, изображение и обычное значение различимы. Не перекрывать стандартные имена среды без необходимости.
- Объяснять незнакомое английское слово. Проверять, что Маша понимает выбранное имя и сама может назвать аналогичную сущность.
- Согласованное форматирование обязательно. Использовать имеющиеся настройки проекта; не устраивать спор о кавычках или переписывание всего файла ради вкуса проверяющего.

## Компоненты и ответственность

- Отдельное окно, форма, таблица или другой самостоятельный смысловой блок интерфейса получает собственный компонент и файл. Границы выбирать по ответственности, данным и поведению, а не по жёсткому количеству строк.
- `App.jsx` постепенно становится местом сборки основных частей приложения. Не добавлять в него всё новое содержимое экранов и все обработчики. При работе над уже существующим крупным блоком сначала выделить разумную часть, необходимую текущей задаче.
- Перед выделением компонента объяснить: за что он отвечает, какие данные получает через props, какими событиями сообщает о действиях, где хранится состояние. После переноса Маша должна суметь проследить этот путь сама.
- Состояние хранить у ближайшего владельца, которому оно нужно. Не дублировать одно и то же состояние в разных местах ради переноса разметки и не вводить глобальное хранилище без задачи, которая его требует.
- Не создавать компонент на каждый тег. Повторяющийся фрагмент выделять, если у него действительно общее назначение; похожий внешний вид сам по себе не требует универсального компонента со множеством переключателей.
- Разделять отображение, обработку действий и обращение к API, когда они появляются. Сетевые операции размещать в модуле по назначению, не копировать адреса и обработку запросов по обработчикам нескольких компонентов.
- На сервере HTTP-обработка, правила приложения и доступ к данным имеют разные ответственности. Простой первый эндпойнт может возвращать значение прямо из контроллера. Когда появляются правила и операции с базой, объяснить выделение сервиса и слоя доступа к данным. Не собирать SQL, правила и HTTP-ответ в одном разрастающемся методе.
- Не создавать пустые слои, интерфейс к каждому классу, общие библиотеки или универсальные механизмы ради «взрослой архитектуры». Каждое разделение должно решать существующую проблему, которую можно объяснить новичку.

## Размещение файлов

Это соглашения для постепенной самостоятельной работы, а не поручение создать сейчас все каталоги или перенести весь проект.

| Область | Куда относится код |
|---|---|
| Запуск фронтенда | `src/main.jsx` |
| Сборка основных частей интерфейса | `src/App.jsx` |
| Конкретная функция приложения | `src/features/<feature>/`: её компоненты, стили и модули, например для обращений к API |
| Компоненты, используемые разными функциями | `src/components/`; переносить туда при реальном общем использовании |
| Стили компонента | Рядом с компонентом; глобальные правила страницы остаются в общих стилях |
| Изображения | Существующая папка `src/assets/`, с понятными именами |
| Сервер | `backend/`; Java-код в `src/main/java/` внутри серверного проекта, пакеты сгруппированы по функции приложения |
| Серверная конфигурация приложения | `backend/src/main/resources/`; локальная инфраструктура отделена от кода приложения |
| Локальная инфраструктура | `backend/_local/`, Compose — `backend/_local/docker/docker-compose.yaml` |

`<feature>` обозначает осмысленное имя части приложения, а не буквальное имя папки. В Java сначала выбрать базовый пакет, затем размещать код функций внутри него. Каталог появляется вместе с нужными файлами; пустое дерево на будущий большой проект не создавать. Не заводить общую папку `utils` для любого кода, которому не нашли назначение.

Для мобильной части согласовать структуру при выборе стека, сохранив те же принципы: понятные имена, ответственность экранов, отделение запросов от отображения. Размещение нового файла Маша должна уметь обосновать.

## Как включать требования в занятие

До написания кода выбрать из этих правил применимые к задаче критерии и явно включить их в задание. Объяснить новые понятия и один приём на небольшом стороннем примере. Код примера также должен соответствовать соглашениям, чтобы не приходилось сразу переучивать Машу.

Если для задачи нужен первый отдельный компонент, props или перенос состояния, это часть учебной работы и времени занятия. Уменьшить объём функционала, когда новых понятий слишком много. Не давать установку «пока складывай всё в один файл, потом разберёмся».

Существующий общий `App.jsx` улучшать по частям при обращении к его блокам. Не требовать исправить весь старый код ради маленькой несвязанной задачи и не делать полную чистку фронтенда условием запуска Java/Spring. Качество нового кода проверяется сразу; связанная с ним необходимая часть старого кода также входит в объём занятия.

## Проверка, исправления и приёмка

1. Прочитать изменённый код и необходимые соседние файлы. Проверить имена, границы ответственности, размещение файлов, передачу данных и сохранение поведения. Не ограничиваться тем, что страница открывается.
2. Для каждого замечания указать место, конкретную проблему, последствие и применимое правило. Объяснить, почему выбранный Машей вариант здесь затрудняет чтение, изменение или проверку, и какую цель должно решить исправление. Фразы «так принято» и «это плохая архитектура» без причины недостаточны.
3. Разделить **обязательные исправления** и **необязательные улучшения**. Нарушение применимого соглашения, неоднозначное имя, смешение самостоятельных ответственностей, неверное размещение или потеря поведения требуют исправления. Равнозначный выбор структуры и личный вкус преподавателя не блокируют приёмку. Если корректных вариантов несколько, принять обоснованный вариант Маши.
4. Сохранить все найденные обязательные замечания в результате дня, а в диалоге разбирать по 1–2 за раз. Попросить Машу самой предложить имя или границу компонента и выполнить правку. Если приём незнаком, сначала объяснить его; не требовать угадать решение и не выдавать готовый патч.
5. После исправления повторно прочитать фактические файлы, проверить все места использования и затронутое поведение. После переноса — также импорты, props и стили. Подходящие существующие проверки, включая lint и сборку, выполняются в рамках общих правил проекта; не добавлять инструменты и тесты ради простого переименования. Невыполненные проверки отмечать честно.
6. Отдельно попросить объяснить, почему изменение помогает. Закрывать замечание после проверки исправления, а навык оценивать по самостоятельности. Устранение замечания по подробной подсказке ещё не означает освоения.

**Статус качества:** «не проверено», «есть обязательные замечания» или «принято». При наличии обязательных замечаний не отмечать задание выполненным/принятым целиком: работающая функция и пройденная проверка качества фиксируются отдельно. Неизвестный результат проверки не обозначать как успешный.

Маша может закончить день в любой момент. Оставшиеся замечания сохраняются с конкретным следующим действием; к ним возвращаются до дальнейшего расширения затронутой части. Это не мешает подготовить честное описание выпуска или продолжать независимую часть обучения. Не считать перенос молчаливой отменой требования и не закрывать замечание только потому, что начался новый день.
